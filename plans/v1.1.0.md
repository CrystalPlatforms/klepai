# PRD — Klepai v1.1.0 (Native Menus)

**Status:** active PRD for v1.1.0, written ahead of implementation (decided 2026-11-06 in a discovery session with the owner; pinned early "in reserve", like v0.1.2, v0.1.4, v0.1.5, v0.1.6 and v1.0.0 were). Implementation lands after the beta line completes — **1.0.0 (the Livebar + the stability gate) ships first**.
**Source of truth:** `plans/prd-post-alpha.md` is the master roadmap; on conflict, the master wins. The menu contents' catalog is `plans/native-menus.md` (owner-authored during discovery) — the catalog lists what the menus contain, this PRD explains and bounds it.
**Predecessor:** v1.0.0 — several v1.1.0 behaviors compose with it (macOS close = hide, story 70; the "agents are running" signal).
**Model:** none external — this is Klepai's own native-chrome work; macOS menu conventions are the reference implementation.

---

## Problem Statement

Klepai is a desktop app that does not speak desktop. There is no native menu bar: a mac user finds no File or Edit menu where the OS has trained them to look for one, and text-editing basics (undo, copy, paste) ride on webview defaults with no visible home. Every action lives only in the app's own chrome — buttons scattered between the sidebar and the panes — with no predictable catalog and no keyboard shortcuts. And quitting is dangerously easy: one accidental Cmd+Q (or the X on Windows) kills every agent still mid-run without a word of warning.

## Solution

**Native Menus.** On macOS, the full native menu bar: the app menu **Klepai** (About Klepai, Check for Updates…, Settings…, Hide Klepai, Quit Klepai) plus **File, Edit, Conversation, Composer, Details, Settings, Window, Help** — every item a catalog entry for something the app already does, wired to the same code paths as the UI buttons, with standard macOS keyboard shortcuts. On Windows and Linux (no system menu bar) the same structure lives behind a new **☰** button in the sidebar header, opening as a native popup menu — plus the app-menu items (About / Check for Updates… / Quit) that platform has nowhere else. Menu items that have nothing to act on stay visible but dim. The one genuinely new behavior is the **quit guard**: quitting on any platform while an agent is still running first asks a native confirmation.

## User Stories

- **71.** *(master, added by this discovery)* As the user on macOS, I want the **native menu bar** — the app menu **Klepai** (About Klepai, Check for Updates…, Settings…, Hide Klepai, Quit Klepai) plus **File, Edit, Conversation, Composer, Details, Settings, Window, Help**, exactly as `plans/native-menus.md` lists them — so that Klepai reads as a real mac app and every action has one predictable address. *(Edit and Window carry the standard system roles; labels in English; the menus are always on — no Settings switch.)*
- **72.** As the user, I want every menu item to **drive the app through the same code path as the UI buttons** — File (New conversation, Search conversations, Hide/Show sidebar, Show/hide details), Conversation (Rename, Export, Delete, Send, Stop generating), Composer (Add attachment, Remove all attachments) — so that the menu is a catalog of real actions, not a parallel implementation.
- **73.** As the user, I want the **Details menu** (Brain, Server, System prompt, Temperature, Context length, CLI agent selection) to **reveal the DetailPane and focus the matching field**, so that the menu navigates instead of duplicating controls.
- **74.** As the user, I want the **Settings menu** (Add server, Defaults ▸ default server / default model / default system prompt, Import skill, Add skill, Clear allowed commands and actions) to **open the Settings dialog directly at the matching section** — Import skill also opens the file picker — and the app menu's **Check for Updates…** to land on Settings → About and run the check, so that configuration is one step away without duplicating Settings UI inside the menu.
- **75.** As the user, I want the **Help menu** to open the project's real addresses in my browser — Website, Official GitHub, CrystalPlatforms' website, CrystalPlatforms' Official GitHub, Create issue, **Contact ▸** (Mail, form on Crystal's landing) and Profiles and social medias — so that support and links live where I look for them.
- **76.** As the user, I want **keyboard shortcuts on the menu items** — Cmd+N (new conversation), Cmd+E (export), Cmd+F (search conversations), Cmd+B (toggle sidebar), Cmd+R (rename conversation), Cmd+, (Settings) — plus the standard roles' shortcuts (Cmd+Z/X/C/V/A, Paste and Match Style, Cmd+M/W/H/Q), so that power use never needs the mouse. *(No conflicts: the app binds no Cmd-shortcuts today.)*
- **77.** As the user, I want menu items to **stay visible but disable themselves when they have nothing to act on** — Stop generating while no stream runs, Send while nothing can be sent, Export / Delete / Rename / the Details items without a selected conversation, Remove all attachments when there are none — so that the menu never pretends an action is possible. *(Native dimming convention; items are never hidden.)*
- **78.** As the user, I want a **quit guard on every quit path on every platform** — macOS Cmd+Q / Quit Klepai, Windows/Linux window X and ☰ → Quit — so that while agents are still running, a **native confirmation dialog** ("agents are working — quit anyway?") stands between my finger and their death; confirming quits for real, cancelling keeps everything alive. *(The one new behavior in v1.1.0. On macOS plain X and Cmd+W keep hiding per story 70 — only real quit paths are guarded.)*
- **79.** As the user on **Windows/Linux**, I want a **☰ button in the sidebar header** opening the **same menu tree as a native popup** — plus About Klepai / Check for Updates… / Quit Klepai, which that platform has no app menu for — so that non-mac users get the identical catalog. *(The popup follows the OS theme, not the app theme — accepted native behavior.)*

## Implementation Decisions

### Goal and shape (discovery Q1–Q4)

- The goal is **native polish + a discoverable catalog of existing actions** — menu items open, focus or trigger what the app already does. The two deliberate exceptions: the quit guard (78) and the Settings deep-links (74).
- The structure: **Klepai | File | Edit | Conversation | Composer | Details | Settings | Window | Help** — nine top menus including the app menu. The owner authored the catalog during discovery and chose to keep their six custom menus 1:1, adding standard Edit and Window rather than merging (Q6).
- **Single-window stays.** "New window" was dropped (Q4): multi-window is an architectural change that would collide with story 70's hide-on-close; parked as a post-1.0 candidate.

### One menu tree, two surfaces (Q10, blueprint)

- The whole tree is **built once in Rust** (Tauri 2's menu API). On macOS it is the app's menu bar; on Windows/Linux the **same menu objects pop up natively** at the ☰ button (blueprint decision: native popup, not a React dropdown). One definition, zero drift between platforms.
- The ☰ lives in the **sidebar header**, beside the existing buttons; no custom titlebar. The popup renders in the **system theme** — accepted, every native app behaves this way.

### Wiring (blueprint components)

- Every item carries an **ID → window event → frontend dispatcher** that calls the **same functions the UI buttons call** — no duplicated logic in either direction.
- **State sync** (77): the frontend pushes enable/disable for state-dependent items; the owner's wording of the rule is "always there, grayed out when there is no available action".
- **Settings deep-links** (74): the Settings dialog accepts an initial tab; Import skill additionally opens the file picker; Check for Updates… opens About (which already hosts the updater) and triggers the check.
- **Details focus** (73): reveal the DetailPane, then highlight the requested field.
- **Help links** (75): system browser via the shell-open path; exact URLs live in the catalog.
- **Accelerators** (76): exactly the agreed set plus system roles — nothing more.

### Quit guard (Q13, blueprint)

- Intercepts **all** quit paths on **all** platforms (78). "Agents are running" comes from the same running-state the sidebar (and the v1.0.0 Livebar) uses — **no second detection path**. Running agents → **native confirm dialog**; Cancel aborts the quit (app, agents, Livebar intact), Confirm proceeds exactly as today. No running agents → quit instantly, no dialog.
- On macOS, window X and Cmd+W keep **hiding** (story 70) — the guard runs only on real quit paths.

### Boundaries

- English labels only; no i18n (explicit future candidate).
- No on/off switch — the menu bar is platform chrome, not a feature (Q12).
- Nothing of v1.0.0 (Livebar) or v1.2.0 (Klep top-bar icon + mini-window) is touched or pre-built; ☰ is a menu trigger, never an agent panel.

## Assumptions

- Tauri 2's menu API covers the full tree on all three platforms (submenus, accelerators, per-item enable/disable, popup). If one predefined role is missing on a platform (e.g. Paste and Match Style), that single role ships as a custom action or drops — an implementation detail, not scope.
- "Agents are running" is readable app-wide from the existing agent-state machinery — CLI processes are spawned and tracked by Klepai itself and the built-in agent state is in-app. **No new detection path.**
- The existing UI handlers (new conversation, search focus, rename, export, send/stop, attachments, Settings tabs, DetailPane fields) are reachable from a dispatcher without refactors beyond adding entry points (verified 2026-11-06: About is a Settings tab; sidebar buttons, search, stop and attachments all exist).
- Menu events keep working while the macOS window is hidden (story 70) — native menus belong to the app process, not the window.
- CI-built Windows/Linux artifacts passing are the accepted compile proof for ☰; functional verification on real Windows/Linux happens opportunistically, not as a release blocker (discovery Q14) — hand-validation stays 1.0.0-gate work.
- Every Help URL resolves (the owner supplied them in the catalog, 2026-11-06).

## Tradeoffs Considered

- **Custom React dropdown for ☰** — rejected (blueprint): a second implementation of the same tree; the native popup is one definition and the honest "native menus" look, at the cost of following the OS theme.
- **"New window" in File** — rejected for v1.1.0 (Q4): multi-window re-architects state and clashes with story 70; parked as a post-1.0 candidate.
- **Hiding inapplicable items** — rejected (77): the catalog stays stable — always visible, dimmed when dead; hiding would make the menu breathe.
- **Always-enabled items** — rejected: dead clicks feel broken; dimming is the native convention.
- **In-app styled quit modal** — rejected (blueprint): at quit time the native dialog is robust on every path and platform; a styled modal is fragile mid-teardown.
- **Menu items mutating settings directly** (e.g. one-click "Clear allowed commands" from the menu) — rejected (Q7): destructive actions keep their home in the dialog, with their confirmations; the menu deep-links there.
- **Merging Composer into Conversation and Details into Settings** — rejected (Q6): the owner kept their structure 1:1; standard Edit and Window joined instead.
- **Menu label i18n** — rejected: the UI is English today; a translation layer is separate future work (Q11).
- **A Settings on/off switch for the menu bar** — rejected (Q12): chrome is not a feature; switching it off would strand shortcut discovery.

## Validation Strategy

### Automated

- **Rust unit test** (the skills-injection pattern): the menu builder produces every catalog item with its ID and accelerator — the full tree from `plans/native-menus.md`, including the Windows/Linux additions (About / Check for Updates… / Quit) and the state-dependent items as present-but-dimmable slots.
- **Vitest:** the dispatcher maps every menu event ID to the correct existing handler; the Settings dialog honors an initial tab; a Details event reveals the pane and marks the target field; the state-sync table dims exactly the right items for a given app state (no stream → Stop dimmed; no selection → Export/Delete/Rename/Details dimmed; no attachments → Remove all attachments dimmed).
- **CI:** green Windows/Linux builds prove the ☰ tree compiles cross-platform.

### HITL (owner — macOS first, Windows/Linux when at hand)

1. macOS: all nine menus appear with the catalog's items; the app menu's About / Check for Updates… / Settings… / Hide / Quit all behave (About lands on its tab, the check runs).
2. Shortcuts: Cmd+N new conversation; Cmd+F focuses search; Cmd+B collapses the sidebar; Cmd+R renames the selected conversation; Cmd+E opens export; Cmd+, opens Settings.
3. Details ▸ Temperature (and each sibling) reveals the DetailPane and highlights the field.
4. Settings ▸ Add server lands on the servers section; Defaults ▸ items land on the matching controls; Import skill opens the picker; Add skill lands on skills; Clear allowed commands lands on the allowed rules.
5. Help: each link opens the browser at the right URL; Contact ▸ Mail opens the mail client, ▸ Form the landing contact; Profiles opens the taplink page.
6. State dimming: idle app → Send/Stop dimmed; streaming → Stop enabled and it really stops; no selection → Export/Delete/Rename/Details dimmed; no attachments → Remove all attachments dimmed.
7. Quit guard: start an agent → Cmd+Q → alert appears → Cancel keeps app and agents alive → Confirm quits for real; repeat via the menu item. Without agents: quit is instant, no dialog.
8. Regression: copy/paste/undo work in the composer (Edit roles); Minimize/Zoom work (Window); X and Cmd+W still hide on macOS with agents alive (story 70).
9. Windows/Linux (CI artifact or when at hand): ☰ in the sidebar header opens the native popup; the tree mirrors macOS plus About / Check for Updates… / Quit; X with agents running alerts first.

## Out of Scope (v1.1.0)

- Multi-window / "New window" (post-1.0 candidate).
- Any new capability behind a menu item (e.g. Find in conversation) — catalog of existing actions only.
- Menu label translations / system-language i18n.
- A Settings on/off switch for menus; custom-styled dropdowns on Windows/Linux.
- The v1.2.0 Klep top-bar icon and mini-window; any change to the v1.0.0 Livebar.
