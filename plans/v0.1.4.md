# PRD — Klepai v0.1.4 (MCP client)

**Status:** active PRD for v0.1.4, written ahead of implementation (decided 2026-10-29 in a discovery session with the owner; pinned early "in reserve", like v0.1.2 was). Implementation order stays v0.1.0 → v0.1.1 → v0.1.2 → v0.1.3 (Brainstorm) → v0.1.4.
**Source of truth:** `plans/prd-post-alpha.md` is the master roadmap; on conflict, the master wins. Stories 48–49 live in the master; stories 62–63 were added to the master by this discovery (originally numbered 57–58; renumbered on 2026-10-29 in the v0.1.5 discovery after a numbering collision with v0.1.3's stories). This document pins down the decided details.
**Predecessor:** v0.1.3 (Brainstorm mode) ships before this version.

---

## Problem Statement

Klepai's model can only use the tools the app ships with. The outside world — GitHub, search, whatever service the user relies on — is out of reach unless they leave Klepai for a CLI agent that happens to carry its own MCP configuration. Modern chat apps solve this with MCP: the user adds a server once and its tools appear wherever they talk.

## Solution

A Settings → **MCPs** view where the user adds their own MCP servers — local (a command) or remote (a URL, like custom connectors in ChatGPT/Claude). Klepai connects to the enabled servers at app startup — a **"Starting MCPs…"** composer placeholder while it works, never blocking anything — and their tools become available to the built-in model in **every mode**, Natural and Agent alike, guarded by the same per-call permission flow the built-in agent already uses.

## User Stories

- **48** *(master)* — as the user, I want a **MCPs** view in Settings where I can add, edit and delete **custom MCP servers** — with **no library of presets** — so that I connect exactly the tools I choose.
- **49** *(master, refined)* — as the user, I want MCP server tools exposed to the AI **via tool-calling in every mode of the built-in model** — Natural chat and agent conversations alike — so that connected tools work wherever I am talking. CLI agents keep their own MCP configuration.
- **62** *(master, added by this discovery; renumbered from 57 on 2026-10-29)* — as the user, I want every MCP tool call in Natural or Agent mode to ask my permission — the composer swaps to Allow/Deny exactly as built-in agent asks do — unless a Standing Allowed rule matches the tool name (`server__tool`) or the conversation is Unrestricted, so that external tools are guarded like built-in ones.
- **63** *(master, added by this discovery; renumbered from 58 on 2026-10-29)* — as the user, I want Klepai to connect to my enabled MCP servers at startup — a **"Starting MCPs…"** composer placeholder until it finishes, nothing blocked meanwhile — and a **red dot** on the Settings icon and the MCPs tab label while any enabled server has a connection error, so that breakage is visible at a glance.

## Implementation Decisions

### Server model (story 48)

- A new `mcp_servers` store; full CRUD in Settings → MCPs (add / edit / delete) plus an **enable/disable toggle** per server. No preset library (master boundary).
- **Remote server:** **URL** + optional **API key / Bearer token** field + a **"Sign in" button (OAuth)** for servers that require it (Q3, Q13).
- **Local server:** **command line** (e.g. `npx -y some-server`) + an optional collapsible **Environment variables** field (`KEY=value`, one pair per line) (Q3, Q20).
- A warning dialog shows **on every add** (not dismissible), worded by server type: local → "this server will run code on your machine"; remote → "what you send will go to an external server" (Q6, Q14). Cancel aborts the add.

### Transport (Q2)

- **stdio** (Klepai spawns the local command) and **streamable HTTP** (remote URL). **No SSE** — legacy transport, out of scope.

### Tools in every mode (story 49)

- Tools from **enabled** servers are advertised to the **built-in model** via tool-calling in **every mode of the built-in brain** — Natural and agent conversations (and Brainstorm once v0.1.3 ships, which precedes v0.1.4).
- **CLI agents are untouched** (Q1): Claude Code and Codex conversations keep their own MCP configuration; Klepai passes nothing to them. Pass-through is a possible later version.
- Tool naming: **`server__tool`** (e.g. `github__create_issue`) — the name the model sees and the string Standing Allowed rules match (Q16).
- Tool calls render as **activity items** in the thread with the server and tool name (Q9) — the same surface that already renders Codex's `mcp_tool_call` items.

### Permissions (Q4, Q5, Q16, Q17)

- Every MCP tool call in Natural/Agent goes through the **existing built-in-agent permission flow**: the composer swaps to **Allow / Deny** (Q17). No new ask UI.
- **Standing Allowed** rules match tool names (`server__tool`) and auto-approve, exactly as they do commands today (Q16).
- **Unrestricted** conversations auto-accept all MCP tool calls, like everything else in that mode (Q5).
- `read_skill` remains the only gateless tool (skills precedent).

### Lifecycle and status (Q15, Q18, Q19)

- At **app startup** Klepai connects to all enabled servers automatically. *(The owner revised the earlier lazy-connect idea during discovery — startup connect is the decided behavior.)*
- While connecting, the composer input placeholder reads **"Starting MCPs…"**; when the connection attempts finish it returns to the normal placeholder — **always**, including on failures. Startup never hangs (Q18).
- **Nothing is blocked** while connecting: typing and sending work normally (Q19). A tool call aimed at a still-connecting server waits within the connect timeout, then returns the error to the model as the tool result.
- Failure surfaces: a **red dot on the Settings icon** and a **red dot on the "MCPs" tab label**, plus per-server error status + message in the MCPs view. The dots clear when the servers connect or are disabled/removed (assumption).
- The MCPs view shows per-server **status + tool count** (e.g. "12 tools") (Q8).

### OAuth (Q13)

- The API-key/Bearer field covers simple auth; the **"Sign in" button** runs the OAuth 2.0 flow from the MCP spec for servers that require it: system browser opens, the app receives the redirect via a local callback, tokens are stored locally. Exact token storage is an implementation decision.

### Scope guard

- v0.1.4 ships **MCP only** — nothing rides along.
- **Tools only** (Q12): MCP resources and prompts each need their own UI surface and are explicitly future scope.

## Assumptions

- `server__tool` naming is unambiguous for the model and for Allowed rules (the owner accepted this example in Q16).
- Startup connect has a timeout (exact value at implementation) so "Starting MCPs…" can never hang indefinitely.
- Tool schemas ride in the request payload — a very large number of servers/tools may grow prompts; observed at implementation, with a hint pattern like `TOOLS_HINT` if it becomes a problem.
- The Rust-side MCP client stack (official SDK vs hand-rolled JSON-RPC over stdio/HTTP) is an implementation decision.
- Free hosted remote MCP servers (e.g. **Neon MCP**) serve as validation servers for the HTTP transport (free-for.dev finding, 2026-10-29).
- v0.1.3 (Brainstorm) will exist before v0.1.4 is implemented, so "every mode" includes it.

## Tradeoffs Considered

- **MCP pass-through to CLI agents** (`--mcp-config` / `-c` flags) — rejected for v0.1.4: CLI agents already have their own config paths; pass-through doubles the surface for little gain (Q1).
- **Tools auto-allowed like `read_skill`** — rejected: the owner chose the explicit per-call gate with the Allowed-rules escape hatch (Q4:3).
- **Lazy connect on first use** — rejected: status + tool counts need connections anyway, and startup connect is the predictable mental model; owner revised the decision mid-discovery (Q15).
- **SSE transport** — rejected: legacy; streamable HTTP is the current standard (Q2).
- **Resources/prompts in v0.1.4** — rejected: each is near-standalone with its own UI; tools first (Q12).
- **API key only (no OAuth)** — rejected: well-known servers (GitHub, Notion, Linear) are OAuth-only (Q13).
- **Blocking input during startup connect** — rejected: connecting must never get between the user and the composer (Q19).
- **Silent failures** — rejected: invisible breakage; the red dots make it discoverable (Q18).
- **Per-tool allowlist per server** — rejected: Standing Allowed by tool name already covers selective trust without a second list (Q16).

## Validation Strategy (HITL)

1. Add a **local stdio server** in Settings → MCPs: the warning dialog shows; after confirming, the row appears with a toggle; enable it.
2. Add a **remote HTTP server** (free hosted, e.g. Neon MCP) with its URL; API key field present; warning shows.
3. Restart the app: the composer shows "Starting MCPs…" and then returns to the normal placeholder; the MCPs view shows status + tool count for both servers.
4. **Natural conversation:** ask the model to use a server tool → the composer swaps to Allow/Deny → **Allow** → an activity item with server and tool name appears → the model uses the result.
5. **Deny** the same ask → the model receives the denial and answers without the tool.
6. Add a Standing Allowed rule for the tool name (`server__tool`) → the same call runs without asking.
7. **Agent-mode** conversation with the built-in brain → the same tool flow works.
8. **Unrestricted** conversation → the tool call runs with zero asks.
9. Break a server (wrong URL / dead command) and restart → the placeholder returns to normal; red dots appear on the Settings icon and the MCPs tab label; the MCPs view shows the per-server error; fixing the server clears the dots.
10. While "Starting MCPs…" shows, type and send a message → it sends normally.
11. **Sign in (OAuth)** on a server that requires it → browser opens, the app regains focus, tools list appears after connect.
12. **Disable** a server → its tools stop being offered; **delete** it → row gone after confirm.

## Out of Scope (v0.1.4)

- MCP for CLI agents (pass-through of servers to Claude Code / Codex).
- MCP **resources and prompts** (future version).
- **SSE** transport.
- MCP preset/curated library; marketplace integration (master Out of Scope stays).
- Permission exceptions beyond Standing Allowed names and Unrestricted.
