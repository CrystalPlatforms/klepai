# PRD — Klepai v0.1.1 (Agent status notifications + needs-input state)

**Status:** active PRD for v0.1.1, the second beta of the post-Alpha line (decided 2026-10-29 in a discovery session with the owner).
**Source of truth:** `plans/prd-post-alpha.md` is the master roadmap; on conflict the master wins — with one explicit exception this document records: story 44's needs-input color is **blue**, not the master's original "orange" (owner decision, Q19; the master has been updated to match).
**Predecessors:** Alpha v0.0.2 (collision guard, `plans/v0.0.2.md`) and v0.1.0 (variant navigation + update banner, `plans/v0.1.0.md`) ship before this version. This discovery was made ahead of their release; the ship order stays v0.0.2 → v0.1.0 → v0.1.1 (Q1 = 1).

## Problem Statement

*(carried from the master)* An agent working in the background is invisible: nothing says it finished or that it is stuck waiting for permission, so the user polls the window. A conversation the user is not looking at can sit finished — or waiting on an allow/deny dialog — with no signal anywhere.

## Solution

Klepai raises a notification when a conversation the user is not viewing **finishes (idle)**, **needs input** (an allow/deny dialog is pending), or **fails (error)** — and stays silent while running. Clicking a notification focuses the window and switches to that exact conversation. In the thread, the dot-matrix loader shows a **needs-input state — all squares pulsing blue** — while a dialog is pending, and the conversation card in the sidebar carries the same blue needs-input status.

## User Stories

- **42** *(master)* — notification when an agent finishes (idle) or needs something (needs input); nothing while Running.
- **43** *(master)* — clicking a status notification focuses Klepai and switches to that exact conversation.
- **44** *(master, amended)* — the agent loader shows a needs-input state — **all squares pulsing blue** — visible in the thread itself. *(The master originally said orange; changed to blue in this session.)*

## Implementation Decisions

### When Klepai notifies (Q3, Q4, Q6, Q15)

- **Trigger condition:** the conversation is in the background — the user is viewing a different conversation *or* the Klepai window is inactive/minimized. The conversation currently on screen never notifies.
- **Events that notify:**
  - **Finished (idle)** — agent work ended (CLI process ended / generation done). All modes notify: agent conversations (built-in and CLI brains) and Natural chat alike; always, with no minimum-duration threshold (Q15 = 1).
  - **Needs input** — an allow/deny dialog is pending. **Only** that: a question asked in plain text does not trigger needs input — it is not reliably detectable, especially for Codex (Q5).
  - **Error** — a failed generation or a CLI process exiting with an error notifies too, as its own "Error" type with the message (Q14 = 1).
- **Never notifies:** while running (master rule); when the user stopped the generation themselves (Stop/abort); on the transient CLI silence watchdog ("stalled").

### Detection per brain (Q13 = 1; the master's riskiest unknown, resolved here)

- **Built-in server agent** (`run_tool_loop`): a pending permission is already tracked in the backend (`AppState.permissions`, `PendingPermission::Loop`); v0.1.1 exposes it to the notification layer (query command or event — implementation choice). Completion: existing `Done`/`AgentDone` stream events; errors: the existing `Error` event.
- **Claude Code CLI:** permission requests are already parsed (`control_request` / `can_use_tool` → `AgentEvent::PermissionRequest`, `app/src-tauri/src/agent.rs`) — full needs-input support.
- **Codex CLI:** its adapter parses activity only and has no approval/question parsing — **idle and error only** on start. Needs-input detection for Codex is deferred (may return in a later version).
- Completion/error events already exist for both pipelines (`AgentDone { aborted, error }`, `Done`, `Error` in `ChatStreamEvent`).

### Delivery per platform (Q7 = 1; master pattern)

- **Windows + Linux:** an app-owned clickable banner following umux's shipped pattern (umux #118): borderless, always-on-top, bottom-right of the work area, auto-dismiss ~5 s, never steals focus. Banners stack when several events arrive. The banner is **silent** (no sound).
- **macOS:** native notification center via `tauri-plugin-notification` — **the plugin is not in the app today** and gets added (Rust dependency, npm package, capability permissions). System sound per the user's settings (default on).
- **Settings:** one toggle in Settings — notifications on/off (Q11 = 3). Off silences all three event types; the in-thread and sidebar states stay (they are UI, not notifications).

### Click behavior (story 43; Q8)

- Clicking a notification (banner or native): bring the window to front and un-minimize it, focus it, and switch to that conversation — the existing navigation path (`setSelectedId` + scroll target in `App.tsx`). Identical on all platforms.
- There is **no tray and no hide-to-tray in v0.1.1**: closing the window quits the app and its agents, so a closed app sends nothing (Q8 = 1).

### Needs-input state in the UI (story 44, amended; Q19, Q20)

- **Color: blue — everywhere.** No orange anywhere for needs input. The in-thread loader shows all squares pulsing blue while an allow/deny dialog is pending; normal phases return once the user decides. Applies to the built-in agent and Claude Code (per detection scope above).
- The dots take their color from CSS (`AgentLoader.tsx` uses `bg-current`), so this is a color change plus pulsing pattern, not a new loader component.
- **Sidebar conversation card:** keeps its existing statuses (running as today, error as today) and gains the needs-input status in blue. **Finished leaves no trace on the card** (Q20 = 1) — the notification is momentary by design.
- Open visual detail for implementation: the permission panel in the thread is amber today (`PermissionAskPanel`); decide during implementation whether it re-accents to blue to match the needs-input state or stays amber.

### Notification content (Q10, Q16 = 1; Q9 = 1)

- Title: **"Klepai"**. Type: **"Finished"** / **"Needs input"** / **"Error"**. Body: the conversation name truncated to ~40 characters ("…" on truncation). One notification per event — no aggregation.

## Assumptions

- Ship order stays v0.0.2 → v0.1.0 → v0.1.1; this PRD was written ahead of their release by owner decision (Q1 = 1).
- Scope stays exactly stories 42–44 — nothing rides along (Q2 = 1).
- Closing the app kills its agents; notifications only come from a running app (no tray in scope).
- "Blue" is the single color for the needs-input state: in-thread loader and sidebar card alike (Q19).
- The master's original "orange" wording for story 44 is superseded by this session; `plans/prd-post-alpha.md` has been updated to match.
- `AppState.permissions` already holds the pending-permission truth for both brains; only a query/event surface to the notification layer is missing.
- The stalled watchdog (CLI silence) is a transient state, not a notification-worthy event.

## Validation Strategy (HITL)

1. Start an agent conversation, switch to another conversation; let the agent finish → a "Finished" notification appears with the conversation name; the conversation you are viewing never notifies.
2. Trigger an allow/deny dialog in a background conversation (built-in agent) → "Needs input" notification; in that conversation's thread all squares pulse blue; after you decide, normal phases return.
3. Same for a Claude Code conversation: permission request in the background → blue pulsing + "Needs input" notification.
4. A Codex conversation finishing in the background → "Finished" notification; a Codex permission state shows no blue state — Codex is idle/error only on start.
5. Force an error (kill the CLI process) → an "Error" notification with the message; the sidebar card shows the red error status as today.
6. Click a notification while Klepai is minimized → the window comes to front, focused, showing that exact conversation.
7. Stop a generation yourself → no notification.
8. Two background conversations end around the same time → two separate notifications; each click lands in its own conversation.
9. Turn notifications off in Settings → nothing fires; turn them on → they work again.
10. macOS: notifications land in the notification center with the system sound; clicking navigates. Windows/Linux: the banner is bottom-right, ~5 s, silent, never steals focus, and banners stack.

## Out of Scope (v0.1.1)

- Tray icon / hide-to-tray / close interception.
- Aggregated notifications; notification history inside the app.
- Needs-input detection for Codex (deferred); detecting plain-text questions from any brain.
- Per-conversation notification settings (the single global toggle is all).
- Any sound configuration (system default only).
- Everything in the master's Out of Scope for the beta line.
