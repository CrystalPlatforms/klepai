# Plan: Klepai v0.1.0 — Variant navigation + update banner

> Source PRD: `plans/betas/v0.1.0.md` (stories 40–41 of the master, `plans/prd-post-alpha.md`). All decisions provenance'd to the 2026-10-27 discovery session; this plan adds no new product decisions.

## Architectural decisions

Durable decisions that apply across all phases:

- **Architecture style**: the existing Tauri split stays untouched — Rust owns persistence and generation (`store.rs` is the sole SQLite owner; command layer streams `ChatStreamEvent`s over a channel), React owns presentation (`ChatPane` drives streams, `MessageView` renders bubbles). Variants are a store/generation concern surfaced to the UI through stream events plus a bubble affordance; the update banner is frontend-only on top of the existing updater deep module.
- **Data model**: variants live in a dedicated SQLite table keyed to the **anchor** assistant message row (the last assistant answer). Each variant row stores: content, thinking, the **model id that produced it**, an **aborted** flag, an ordinal, and a **visible** marker — exactly one variant per anchor is visible. Entity name: `MessageVariant` (Rust struct + TS mirror in `app/src/types.ts`, kept in sync per the file's own rule).
- **Context invariant (the load-bearing trick)**: the anchor message row's content **always mirrors the visible variant's content**. History assembly (`list_messages`) therefore stays a flat path with zero new logic — "the model sees the displayed variant" holds by construction, and pruning-at-send reduces to deleting variant rows.
- **Schema migration**: one guarded column/table addition in the store's idempotent migrate path (pragma-check pattern already used for `skill_name`); older database files migrate in place on reopen.
- **Scope lock (Q2)**: v0.1.0 is exactly variants + banner — nothing rides along. No keyboard shortcuts, no background update checks, no conversation trees, no auto-install.
- **Integrations**: update flow reuses `app/src/lib/updater.ts` as-is (preflight → `runCheck` → `runInstall` + relaunch; "up to date" until a signed release ships `latest.json` is expected, not a bug). "See what's new" opens the repo's GitHub Releases page. Banner placement follows umux's shipped banner pattern (reference repo: `~/Documents/umux`).

## Phase 1: Variants tracer bullet — regenerate keeps, navigates, persists

**User stories**: 40

### What to build

The thinnest end-to-end path: clicking regenerate on the last assistant answer **keeps the old answer as a stored variant** instead of deleting it, streams the new answer, and the last bubble grows `<` `>` controls with an "n/total" readout and per-variant **model label**. Navigating marks the shown variant visible; the visible choice and all variants survive an app restart. Regenerate works repeatedly — each click appends another variant (first click turns the original answer into variant 1).

The generation command captures the resolved model at generation time so each variant can carry its model label (messages have no model column today — the label is stored per variant, not per message).

### Assumptions carried in

- The existing regenerate/stream flow (history rewrite event, `done` event) works; this phase changes what happens to the displaced answer, not the streaming machinery.
- The store's idempotent migration pattern handles the new table on reopen.
- Navigation renders on the **last** assistant answer only; older bubbles never show controls (master boundary).

### Out of scope for this phase

- Aborted generations as variants (Phase 2).
- Pruning at send (Phase 3) — after a follow-up message the variants simply stop rendering; DB cleanup comes later.
- Streaming lock and the 10-variant cap (Phase 4).
- Update banner (Phase 5, fully independent).

### Acceptance criteria

- [ ] Regenerating a conversation whose last message is an assistant answer keeps the displaced answer as a variant row and ends with exactly one visible variant whose content equals the anchor row's content — [test: `app/src-tauri/tests/control.rs`]
- [ ] Variants, their ordinals and the visible marker survive store close + reopen (restart equivalence) — [test: `app/src-tauri/tests/store.rs`]
- [ ] The last assistant bubble renders `<`/`>` with a correct "n/total" readout and the model label of the shown variant; stepping updates content, readout and visible marker — [test: `app/src/components/MessageView.test.tsx` (new)]
- [ ] Each variant's stored model id matches the model active when it was generated — [test: `app/src-tauri/tests/control.rs`]
- [ ] HITL: PRD validation scenarios 1 (three regenerates → "1/3 → 2/3 → 3/3", thread otherwise unchanged) and 6 (restart keeps variants + visible one)

## Phase 2: Aborted generations become variants

**User stories**: 40

### What to build

Pressing **Stop** mid-generation keeps the partial answer as a variant carrying the **"aborted"** marker next to its model label — an aborted attempt is evidence, not garbage. A zero-content abort creates no variant (nothing worth keeping). The partial text lands in the same navigation ring as complete variants.

### Assumptions carried in

- Phase 1's variant table, navigation and visible-marker mechanics work unchanged.
- The stream already reports aborted completions (`done` carries an `aborted` flag); this phase only changes what the abort path persists.

### Out of scope for this phase

- Any resume/continue-from-partial behavior — an aborted variant is a kept snapshot only.
- Different retention rules for aborted vs complete variants (same FIFO cap applies in Phase 4).

### Acceptance criteria

- [ ] An aborted generation with non-empty partial content persists as a variant with the aborted flag set; a zero-content abort creates no variant row — [test: `app/src-tauri/tests/control.rs`]
- [ ] The bubble shows the "aborted" marker beside the model label for aborted variants, absent for complete ones — [test: `app/src/components/MessageView.test.tsx`]
- [ ] HITL: PRD validation scenario 2 (stop midway → partial answer survives as a variant marked "aborted")

## Phase 3: Send prunes variants; the displayed one continues

**User stories**: 40

### What to build

Sending a follow-up message removes **all** variants of the previous answer — the visible one's text simply stays as the message (already true by the anchor-mirrors-visible invariant; this phase adds the row cleanup). Navigation disappears the moment the answer is no longer the last, and the model's next reply demonstrably reacts to the displayed variant's content. The DB stays clean by design: pruning happens at send, not lazily.

### Assumptions carried in

- Phase 1's context invariant: the anchor row already holds the visible variant's text, so context correctness needs no new code — only the variant-row deletion is new.
- Sending a message when the previous answer was never regenerated (no variants) is a no-op for this logic.

### Out of scope for this phase

- Any "recover pruned variants" affordance — pruning is silent by decision (owner: "it stays on the one that was displayed last").
- Pruning across conversation forks (fork copies a byte-identical range and is untouched by variant logic).

### Acceptance criteria

- [ ] After sending a follow-up, every variant row of the previous answer is gone and the answer message's content equals the previously visible variant — [test: `app/src-tauri/tests/control.rs`]
- [ ] Navigation controls render only on the last assistant answer; once a new message exists, the older bubble shows none — [test: `app/src/components/MessageView.test.tsx`]
- [ ] HITL: PRD validation scenario 3 (switch to variant 1 → follow-up answer reacts to variant 1; navigation gone, variants gone)

## Phase 4: Hardening — streaming lock and the 10-variant cap

**User stories**: 40

### What to build

Two guardrails from the PRD: `<` `>` are **disabled while a generation streams** (they return when the stream ends), and variants cap at **10 FIFO** — creating the 11th drops the oldest; the readout never exceeds "/10". Both protect the Phase 1 ring from racing the stream or growing unbounded.

### Assumptions carried in

- Phases 1–3: the variant ring, abort handling and pruning all work; this phase only bounds them.
- The streaming-state signal the composer already uses (a run in flight) is the same signal the controls read.

### Out of scope for this phase

- Keyboard shortcuts (explicitly out of v0.1.0, Q7).
- Any configurable cap — 10 is hard-coded per decision.

### Acceptance criteria

- [ ] The 11th variant drops the oldest; variant count never exceeds 10 and ordinals stay contiguous — [test: `app/src-tauri/tests/store.rs`]
- [ ] `<`/`>` render disabled during a streaming regeneration and enabled after `done` — [test: `app/src/components/MessageView.test.tsx`]
- [ ] HITL: PRD validation scenarios 4 (11 regenerates → oldest falls off, readout never exceeds "/10") and 5 (controls disabled mid-stream, back after)

## Phase 5: Update banner at launch (independent of Phases 1–4)

**User stories**: 41

### What to build

At app start the app runs **one** update check through the existing updater deep module and, on an "available" verdict, shows an **in-window banner** (umux's shipped banner pattern — not an OS toast) with the new version and two actions: **Install** (the existing signature-verified download-apply-relaunch flow, progress readout included) and **See what's new** (opens the GitHub Releases page). The banner's X dismisses it **for the session only** — no persistence; it returns at the next launch for as long as the update is pending. Settings → About keeps its **Check for updates** button and its states untouched; the banner adds a mount point, it does not fork the state machine. No banner on "up-to-date", "no-release", "not-configured" or error verdicts — quiet states stay quiet outside About.

### Assumptions carried in

- `updater.ts` exposes everything needed: `runCheck` resolves to `available {version}` or a quiet/error state; `runInstall` + relaunch already drive About's install button.
- Until a signed release publishes `latest.json`, every check lands on a quiet verdict and no banner ever shows — expected pre-release behavior per the PRD.
- "Check timing: app start only" (Q10) — no periodic re-check anywhere in this phase.

### Out of scope for this phase

- Auto-install, background/periodic checks (explicitly out of v0.1.0).
- Changelog rendering inside the banner — "See what's new" is an external link, nothing is fetched.
- Any change to About's existing check/install UI.

### Acceptance criteria

- [ ] A component mounting the banner with a fake updater API: renders with the version on `available`; renders nothing on `up-to-date`/`no-release`/`not-configured`; runs the check exactly once per mount — [test: `npm test` (vitest, new banner test)]
- [ ] Install triggers the existing install flow with progress text and relaunch; See what's new issues the external open of the GitHub Releases URL; X hides the banner for the component's lifetime with no persisted state — [test: same vitest suite, fake API asserts each call]
- [ ] HITL: PRD validation scenarios 7 (with a `latest.json` publishing a newer version: banner at launch, Install completes the update, See what's new opens GitHub Releases, X hides until next launch) and 8 (About's **Check for updates** still works as before)
