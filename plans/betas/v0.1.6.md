**Status:** active PRD for v0.1.6, written ahead of implementation (decided 2026-11-04 in a discovery session with the owner; pinned early "in reserve", like v0.1.1–v0.1.5). Implementation order stays v0.1.0 → v0.1.1 → v0.1.2 → v0.1.3 (Brainstorm) → v0.1.4 (MCP) → v0.1.5 → v0.1.6.

## Problem Statement

*(carried from the master, narrowed by this discovery)* The landing shows a roadmap, but a visitor cannot see what changed **between shipped versions** — release history lives only on GitHub Releases. The page also quietly lies in details: the footer still says "Alpha v.0.0.1" while v0.0.2 shipped on 2026-11-02, the roadmap marks v0.0.2 as "now", and the blurbs for v0.1.1 (orange loader), v0.1.3 ("model proposes several directions") and v0.1.5 ("applied live") drifted from what their discoveries later decided.

## Solution

A static **Changelog** section on `klepai.pages.dev` — one hand-edited paragraph per released version, newest first, each linking to its GitHub release page — sitting **above** the Roadmap, which keeps only future versions. Alpha (v0.0.1–v0.0.2) is one collective entry with two release links. A **"Latest: vX.Y.Z" chip** beside the download buttons becomes the page's only version display; the stale footer version and the drifted roadmap wording are fixed in the same pass. No new JS, no GitHub API — the page stays one static `index.html`, and every future entry is drafted during /release-product and approved in the form.

## User Stories

- **52** *(master, reworded)* — a **Changelog** section on the landing: every released version as a short 1–3 sentence paragraph linking to its GitHub release page, newest first; Alpha (v0.0.1–v0.0.2) as one collective entry carrying two small release links; the section sits above the Roadmap, which lists only future versions. Static hand-edited HTML — no GitHub API, no added JS.
- **65** *(master, added by this discovery)* — a **"Latest: vX.Y.Z" chip** beside the download buttons, updated by hand with each release, so the visitor knows which version the buttons fetch. The chip is the landing's only version display — the footer drops its hardcoded one.

## Implementation Decisions

### Section layout (Q2=1, Q3=2, Q11=1)

- Page order stays hero → features → extras → first-run → **Changelog → Roadmap → CTA (downloads)** — the changelog goes between "First run" and Roadmap.
- The changelog carries **only shipped** versions; the roadmap keeps **only future** ones (v0.1.0 → 1.0.0 → after). The "now" marker on v0.0.2 leaves with the entry it marks.
- The header nav (today: Features, Roadmap — `index.html:502`) gains a **Changelog** link (new `#changelog` anchor).

### Entries (Q4=1, Q5=2, Q6=1, Q12=2)

- One **short paragraph (1–3 sentences)** per version, roadmap style — feature names bolded.
- List: every beta v0.1.x individually, plus **one collective "Alpha (v0.0.1–v0.0.2)"** entry whose body covers the Alpha feature set and the collision guard, with two small links (**v0.0.1 →**, **v0.0.2 →**) to the release pages.
- Every other entry links to its release page (`github.com/CrystalPlatforms/klepai/releases/tag/vX.Y.Z`); the link format stays valid even when committed slightly before the release publishes — it resolves once the release is out.
- **Newest first**; new entries are prepended at each release.
- At v0.1.6's implementation the section starts with exactly **one entry** (the collective Alpha one) — v0.1.0+ entries appear as those versions actually ship, written from their PRDs at that moment.

### The "Latest" chip (Q8=1, Q9=2)

- A chip beside the CTA download buttons: **"Latest: vX.Y.Z"**, text hand-edited with each release (same commit as the changelog entry).
- **No OS detection** — the three download buttons stay equal (Q9=2).
- The footer drops its hardcoded "Alpha v.0.0.1" (`index.html:726`) — the chip is the page's single version display.

### Cleanup riding along (accepted in-session, no veto)

- Roadmap wording synced with the master stories: v0.1.1 → needs-input loader **blue** (not orange); v0.1.3 → the full **Brainstorm pipeline** (Ask → Blueprint → Carve → Dispatch → TDD → Ship), not "proposes several directions"; v0.1.5 → theme via **input + Apply** plus the light/dark toggle, not "applied live".

### The release flow around the changelog (Q7=2, Q10=2, Q13=1)

- At every release the changelog entry + chip bump are **drafted by the agent during /release-product** and shown in the confirmation form; on approval they ride the version-bump commit.
- **Deploy stays manual** (`wrangler pages deploy` — no deploy automation exists in the repo): the flow ends with a reminder to deploy the landing so the entry actually goes live.
- The rule is recorded **project-side** (this PRD + project `CLAUDE.md`); the global release-product skill stays untouched.

### Boundaries

- The landing stays one static `index.html` (inline CSS, no build step, no backend, no cookies) — story 38's constraints hold; zero new JavaScript (the existing download-loading snippet stays the page's only script).
- English only — the landing's language.

## Assumptions

- A GitHub release exists for every version listed (verified today for v0.0.1 and v0.0.2; future versions create theirs as part of the release flow).
- The release-tag link format (`/releases/tag/vX.Y.Z`) stays stable.
- By the time v0.1.6 ships, v0.1.0–v0.1.5 exist, so the changelog and the chip show whatever is actually latest then — nothing is pre-filled from the roadmap now.
- Implementation order unchanged; v0.1.6 work starts after v0.1.5 ships.

## Tradeoffs Considered

- **GitHub Releases API in the browser** — rejected (Q2=1): raw `--generate-notes` bodies are not umux-style summaries, and the page would gain a network dependency, JS and rate-limit edge cases for zero editorial control.
- **One merged "Releases & roadmap" timeline** — rejected (Q3=2): two clean sections read better than one mixed one.
- **Bullet lists per version** — rejected (Q4=1): paragraphs match the roadmap's existing style and stay compact.
- **OS detection highlighting the visitor's button** — rejected (Q9=2): user-agent sniffing misfires, and three equal buttons are already clear.
- **Recording the changelog flow in the global /release-product skill** — rejected (Q13=1): project rules live project-side; the skill stays generic.
- **Keeping the footer's version string** — rejected: two places to update means one goes stale again; the chip is the single source.

## Validation Strategy (HITL)

1. Open the landing: a **Changelog** section sits between "First run" and Roadmap, newest version first; the nav links to it.
2. Every entry is 1–3 sentences and its release link opens the right GitHub release page; the Alpha entry carries working **v0.0.1 →** and **v0.0.2 →** links.
3. The Roadmap lists only future versions (v0.1.0 upward) — no shipped entries, no "now" marker, descriptions matching the decided designs (blue loader, Brainstorm pipeline, Apply + toggle).
4. A **"Latest: …"** chip sits beside the download buttons showing the newest release; the footer shows no version.
5. The page loads with zero console errors and no script beyond the existing download snippet; all other sections unchanged.

## Out of Scope (v0.1.6)

- OS detection on the download buttons; file sizes, checksums, per-OS install instructions (Q1=1, Q9=2).
- Dynamic changelog from the GitHub API; embedding full release notes; an RSS/Atom feed of releases.
- Any landing redesign beyond the decided sections; theming or language changes.
- Everything in the master's Out of Scope for the beta line.
