# Plan: Klepai v0.1.1 — Agent status notifications + needs-input state

> Source PRD: `plans/betas/v0.1.1.md` (stories 42–44 of the master, `plans/prd-post-alpha.md`). All decisions provenance'd to the 2026-10-29 discovery session; this plan adds no new product decisions. Per AUTOM FAST mode, issues here are implemented **without tests** — the version's test pass happens at the end, driven by the "Indicated tests" section below.

## Architectural decisions

Durable decisions that apply across all issues:

- **Architecture style**: the existing Tauri split stays untouched — Rust owns generation and permission truth (`AppState.permissions`, `PendingPermission` in `app/src-tauri/src/commands.rs`, stream events `Done` / `AgentDone { aborted, error }` / `Error` / `PermissionRequest` in `ChatStreamEvent`), React owns presentation. Notifications are a thin layer bridging the two.
- **Event surface over polling**: the backend already holds the completion, error and pending-permission truth, but its stream channels only reach the conversation the frontend currently listens to. v0.1.1 adds one **global Tauri event** (e.g. `conversation-lifecycle`) emitted backend-side whenever a conversation finishes, fails, or a pending permission is set/cleared — payload: conversation id, conversation name, event kind (`finished` | `needs_input` | `needs_input_cleared` | `error`), and an optional error message. The frontend decides whether to notify (background filter + settings toggle); the backend never needs to know window state.
- **Aborted runs never notify**: `AgentDone { aborted, .. }` already distinguishes user stops; the aborted path emits no `finished`/`error` lifecycle event. The stalled CLI watchdog is a transient state and stays silent.
- **Codex scope falls out for free**: Codex's adapter never populates `AppState.permissions`, so `needs_input` events never fire for it; idle/error work from day one. No Codex-specific code.
- **Delivery is a frontend platform switch**: on macOS, native notifications via `tauri-plugin-notification` (new: Rust dep + npm package + capability entry); on Windows/Linux, an app-owned clickable banner following umux's shipped pattern (reference repo: `~/Documents/umux`, umux #118). One decision layer feeds both.
- **Blue is the single needs-input color** (owner decision, Q19 — supersedes the master's original "orange"): in-thread loader and sidebar card alike. The loader dots already take color from CSS (`bg-current` in `AgentLoader.tsx`), so this is a color + pulsing pattern change, not a new loader component.
- **UI state ≠ notifications**: the loader and sidebar needs-input states render regardless of the settings toggle; the toggle silences only the notification delivery layer.
- **Scope lock (Q2)**: exactly stories 42–44 — no tray, no hide-to-tray, no aggregation, no notification history, no per-conversation settings, no sound configuration, no plain-text question detection.

## Package: BACKEND

### Issue B1 — Global conversation lifecycle event surface

**Label**: enhancement

**Description**: The backend emits one global Tauri event, `conversation-lifecycle`, whenever a conversation reaches a notification-worthy state: **finished** (agent run or natural chat generation completed, `AgentDone` non-aborted / `Done`), **error** (failed generation or CLI process exiting with an error, message included), and **needs input** / **needs input cleared** (a `PendingPermission` is inserted into or removed from `AppState.permissions` — covering both `PendingPermission::Loop` and `PendingPermission::Cli`). User-aborted runs (`aborted = true`) emit nothing, and the stalled watchdog stays silent. The payload carries the conversation id, conversation name, kind, and optional message.

**Acceptance criteria**:

- [ ] Completing a generation (agent or chat) emits `conversation-lifecycle` with kind `finished` and the correct conversation id and name
- [ ] A failed generation or CLI error emits kind `error` with the error message in the payload
- [ ] Inserting a pending permission (built-in loop or CLI `control_request`) emits kind `needs_input`; resolving it emits `needs_input_cleared`
- [ ] An aborted run (`Stop` pressed) emits no lifecycle event at all
- [ ] The event fires regardless of which conversation the frontend is currently streaming (a background conversation's finish is observable by a listener that never opened its stream channel)
- [ ] A Codex conversation never emits `needs_input` (its adapter does not populate `AppState.permissions`)

**Files/scope**: `app/src-tauri/src/commands.rs` (emission points at the existing `AgentDone`/`Done`/`Error` send sites and permission insert/remove sites), `app/src-tauri/src/lib.rs` (event name constant if desired), `app/src-tauri/tests/permissions.rs`, `app/src-tauri/tests/control.rs` (test hooks at the end-of-version test pass). Reference: umux #118's lifecycle event pattern where useful.

### Issue B2 — Wire `tauri-plugin-notification` (macOS native delivery groundwork)

**Label**: enhancement

**Description**: Add `tauri-plugin-notification` to the Tauri app: the Rust dependency and plugin registration in the builder, the `@tauri-apps/plugin-notification` npm package, and the notification permission entry in the capability file. No sending logic here — only the plumbing so the frontend delivery layer can request and post native notifications on macOS.

**Acceptance criteria**:

- [ ] The plugin is registered in the Tauri builder and the npm package is installed and importable from frontend code
- [ ] The capability file grants the notification permission
- [ ] The app builds and runs with the plugin present and no behavioral change elsewhere
- [ ] `isPermissionGranted` / `requestPermission` round-trip works on a dev run (HITL check on macOS at test pass)

**Files/scope**: `app/src-tauri/Cargo.toml`, `app/src-tauri/src/lib.rs`, `app/src-tauri/capabilities/`, `app/package.json`. Independent of B1.

## Package: FRONTEND

### Issue F1 — Settings toggle: notifications on/off

**Label**: enhancement

**Description**: One toggle in the Settings dialog switches all v0.1.1 notifications on or off. Off silences all three event types (finished, needs input, error) but leaves the in-thread blue loader and the sidebar needs-input status untouched — those are UI, not notifications. The setting persists like the existing settings.

**Acceptance criteria**:

- [ ] The Settings dialog shows a single notifications on/off toggle, default on
- [ ] The toggle's value persists across an app restart
- [ ] With the toggle off, no notification (banner or native) is shown for any of the three event types
- [ ] With the toggle off, the in-thread blue loader and the sidebar needs-input status still render

**Files/scope**: `app/src/components/SettingsDialog.tsx`, settings persistence in `app/src/lib/` (same mechanism as existing settings), `app/src/App.tsx` (state plumbing). Independent of all other issues.

### Issue F2 — Needs-input loader state: all squares pulsing blue (story 44)

**Label**: enhancement

**Description**: While an allow/deny dialog is pending in the conversation currently open in the thread, the dot-matrix loader switches to a needs-input state: **all nine squares pulsing blue, in sync**. Normal phase patterns return the moment the user decides (permission resolved). Applies to the built-in agent and Claude Code conversations; Codex never shows it. During implementation, decide whether `PermissionAskPanel` re-accents from amber to blue to match (owner left this open in the PRD) — either choice is acceptable, document the pick in the commit.

**Acceptance criteria**:

- [ ] `AgentLoader` supports a needs-input type whose nine squares pulse (opacity oscillation) in sync, colored blue via CSS (`bg-current` under a blue text/`text-*` class), with no X pattern and no phase cycling
- [ ] With an allow/deny dialog pending in the open thread, the loader shows the blue pulsing state instead of the normal phase pattern
- [ ] Resolving the dialog returns the loader to the normal phase patterns immediately
- [ ] A Codex conversation never shows the needs-input state
- [ ] No orange is introduced anywhere for needs input

**Files/scope**: `app/src/components/loaders/AgentLoader.tsx` (new `LoaderType` + keyframes), `app/src/components/ChatPane.tsx` (`PermissionAskPanel` wiring around line 2266; the panel component at line 2921 is where the amber accent decision lands), `app/src/components/loaders/phases.ts` if phase state lives there. Independent of the notification issues; uses the already-streaming `PermissionRequest` events for the open thread.

### Issue F3 — Background-notification decision layer

**Label**: enhancement

**Description**: The frontend listens to the global `conversation-lifecycle` event and decides whether to notify. Notify only when the conversation is in the background: the user is viewing a different conversation, or the Klepai window is inactive/minimized. The conversation currently on screen never notifies. One notification per event — no aggregation. Content: title "Klepai"; type line "Finished" / "Needs input" / "Error"; body is the conversation name truncated to ~40 characters with "…" on truncation. The layer respects the settings toggle from F1 and hands accepted events to the delivery layer (F4/F5).

**Acceptance criteria**:

- [ ] A `finished` event for a conversation the user is not viewing produces a notification; the same event for the viewed conversation produces none
- [ ] With the window minimized or unfocused, an event for the currently selected conversation still notifies
- [ ] The settings toggle off suppresses delivery for all three event kinds
- [ ] Body text truncates the conversation name to ~40 characters with "…"; title is "Klepai"; the type string is exactly "Finished", "Needs input", or "Error"
- [ ] Two events arriving near-simultaneously produce two separate notifications
- [ ] `needs_input_cleared` events never notify

**Files/scope**: new module `app/src/lib/notifications.ts` (decision logic, unit-testable), `app/src/App.tsx` (listener wiring). Depends on B1; independent of F1's internals (reads the toggle state only).

### Issue F4 — Windows/Linux app-owned banner delivery

**Label**: enhancement

**Description**: On Windows and Linux, accepted notifications render as an app-owned clickable banner: borderless, always-on-top, bottom-right of the work area, auto-dismissing after ~5 s, never stealing focus, silent. Multiple banners stack (vertically) when several events arrive close together. Clicking a banner is handled by F5's click behavior.

**Acceptance criteria**:

- [ ] On Windows/Linux an accepted event shows a banner in the bottom-right of the work area: borderless, always-on-top, no focus steal, no sound
- [ ] The banner auto-dismisses after ~5 seconds
- [ ] Two events arriving close together produce two stacked banners (no overlap, no replacement)
- [ ] The banner shows the "Klepai" title, the type line and the truncated conversation name
- [ ] The banner is clickable and exposes the conversation id to the click handler

**Files/scope**: new `app/src/components/NotificationBanner.tsx` (+ state in `App.tsx` or a small manager in `app/src/lib/notifications.ts`); positioning via the Tauri window API (outer position of the work area's bottom-right). Depends on F3.

### Issue F5 — Click behavior: focus, un-minimize, navigate (story 43)

**Label**: enhancement

**Description**: Clicking any notification — banner on Windows/Linux or native on macOS — brings the Klepai window to front, un-minimizes and focuses it, and switches to that exact conversation using the existing navigation path (`setSelectedId` plus the scroll target in `App.tsx`). Identical behavior on all platforms. No tray, no hide-to-tray: closing the window quits the app and its agents, so a closed app sends nothing.

**Acceptance criteria**:

- [ ] Clicking a banner/native notification for conversation X while Klepai is minimized un-minimizes the window, focuses it, and shows conversation X scrolled into view
- [ ] Clicking while the window is simply behind other windows brings it to front and navigates to X
- [ ] Behavior is identical for banner (Windows/Linux) and native (macOS) notifications
- [ ] Dismissing a banner without clicking (auto-dismiss timeout) does not navigate or focus the window
- [ ] No tray icon or close interception is added

**Files/scope**: `app/src/App.tsx` (reuse the existing `setSelectedId` + scroll navigation), `app/src/components/NotificationBanner.tsx` (click wiring from F4), `app/src/lib/notifications.ts` (shared click handler used by both deliveries; native click via the plugin's action handling on macOS). Depends on F3 and F4.

### Issue F6 — macOS native notification delivery

**Label**: enhancement

**Description**: On macOS, accepted notifications go through `tauri-plugin-notification` to the native notification center: title "Klepai", body combining the type line and the truncated conversation name, system sound per the user's settings (default on — no custom sound code). Clicking routes through F5's shared handler.

**Acceptance criteria**:

- [ ] On macOS an accepted event lands in the notification center with the correct title and body
- [ ] The system sound plays per macOS notification settings (no app-side sound code)
- [ ] Clicking the native notification triggers the same focus + navigate behavior as the banner
- [ ] Windows/Linux delivery is unchanged by this issue (platform switch only)

**Files/scope**: `app/src/lib/notifications.ts` (delivery branch on platform), `app/src/components/NotificationBanner.tsx` untouched. Depends on B2 and F3; parallels F4.

### Issue F7 — Sidebar needs-input status on the conversation card

**Label**: enhancement

**Description**: The sidebar conversation card keeps its existing statuses (running as today, red error as today) and gains a **blue needs-input status** shown while that conversation has a pending permission — visible regardless of the settings toggle and regardless of which conversation is open. Needs input is driven by the global `needs_input` / `needs_input_cleared` events (B1), so it works for background conversations too. Finished leaves no trace on the card: nothing changes visually on completion.

**Acceptance criteria**:

- [ ] A conversation with a pending permission shows a blue needs-input status on its sidebar card, including when another conversation is open
- [ ] Resolving the permission clears the status
- [ ] The red error status and the running indicator behave exactly as today
- [ ] A conversation finishing (idle) changes nothing on the card
- [ ] The needs-input status renders even with the notifications toggle off

**Files/scope**: `app/src/components/Sidebar.tsx` (props pattern mirrors `errorIds`), `app/src/App.tsx` (a `needsInputIds: Set<number>` maintained from the B1 listener). Depends on B1; independent of F3–F6.

**Frontend build order**: F1, F2 (independent) → F3 (needs B1) → F4, F7 (need F3 / B1) → F5, F6 (need F4 + F3).

## Indicated tests

Run at the end of the version, after all issues are implemented (FAST mode — tests come last):

1. **Rust backend** (from `app/src-tauri/`): `cargo test` — existing suites (`permissions.rs`, `control.rs`, `agent.rs`) stay green, plus new lifecycle-event tests: finish/error/needs-input emission, aborted-run silence, background observability.
2. **Frontend unit tests** (from `app/`): `npm test` (vitest) — existing suites stay green, plus new tests for the decision layer (`app/src/lib/notifications.test.ts`: background filter, toggle suppression, ~40-char truncation, no aggregation), the needs-input loader type, the sidebar status set, and the settings toggle.
3. **Type check + build** (from `app/`): `npm run build` (runs `tsc --noEmit && vite build`).
4. **Full app build**: `npm run tauri build` or a dev run (`npm run tauri dev`) to verify the plugin wiring compiles and the capability file is valid.
5. **HITL**: the source PRD's Validation Strategy, scenarios 1–10 (background finish, built-in + Claude Code needs input with blue pulse, Codex idle-only, forced error, click-from-minimized navigate, no notify on self-stopped, two stacked notifications, settings toggle, platform delivery details).
