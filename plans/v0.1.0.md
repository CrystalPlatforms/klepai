# PRD — Klepai v0.1.0 (Variant navigation + update banner)

**Status:** active PRD for v0.1.0, the first beta of the post-Alpha line (decided 2026-10-27 in a discovery session with the owner).
**Source of truth:** `plans/prd-post-alpha.md` is the master roadmap; on conflict, the master wins. Stories 40 and 41 live in the master; this document pins down their decided details.
**Predecessor:** Alpha v0.0.2 (agent collision guard, `plans/v0.0.2.md`) ships before this version.

---

## Problem Statement

*(carried from the master)* A weak answer can only be overwritten, not kept beside its retry. And when the updater detects a new version, the only way to learn about it is opening Settings → About — updates do not announce themselves.

## Solution

Regenerating the last assistant answer keeps the old answer as a **variant**, navigable with `<` `>` buttons and a "2/3" readout, labelled with the model that produced it. A new-version banner appears in the app window at launch when the updater finds a release, with **Install** and **See what's new** actions.

## User Stories

- **40** *(master)* — variant navigation on the last assistant answer with `<` `>` and a position readout, so retries can be compared instead of lost.
- **41** *(master)* — update-available banner in the app window; the existing **Check for updates** button in About stays.

## Implementation Decisions

### Variants (story 40)

- **What creates a variant:** clicking regenerate, **and** an aborted generation (Stop) — the partial answer is kept as a variant too. Aborted variants carry an **"aborted"** marker next to the model label (default accepted in discovery).
- **Where:** only the **last** assistant answer carries variants — no mid-thread variant trees (master: a conversation-tree engine was rejected as overkill).
- **Pruning:** sending a new message removes all variants of the previous answer, keeping only the one that was visible at that moment (owner: "the variants are removed and it stays on the one that was displayed last").
- **Context semantics:** the **displayed** variant is what the model sees in history for the next message (Q5).
- **Navigation lock:** `<` `>` is disabled while a generation is streaming; it comes back when the stream ends (Q6).
- **Controls:** buttons on the message bubble only — **no keyboard shortcuts** in v0.1.0 (Q7).
- **Variant label:** model name per variant (Q8); position readout "n/total" as in the master story.
- **Limit:** 10 variants, FIFO — the oldest drops when an 11th is created (Q9).
- **Storage:** variants on the message row, one marked visible (master decision, unchanged). Pruning at send time keeps the DB clean; variants and the visible marker survive a restart.

### Update banner (story 41)

- **Check timing:** at app start **only** — no background periodic check (Q10). The banner appears only if a new version is known at launch; the **Check for updates** button in Settings → About stays for manual checks.
- **Actions:** two — **Install** (runs the existing signature-verified updater flow from `app/src/lib/updater.ts`) and **See what's new** (opens the GitHub Releases page) (Q11).
- **Dismiss:** closing the banner (X) hides it for the session; it **returns at the next app launch** for as long as the update is still pending (Q12).
- **Look & placement:** follows umux's shipped banner pattern; an in-window element, not an OS toast (master decision). Until a signed release ships a `latest.json` asset, the updater reports "up to date" and no banner appears — expected pre-release state, not a bug.

## Assumptions

- Variants stay scoped to the last assistant answer; the rest of the thread is immutable (master boundary, reconfirmed 2026-10-27).
- Aborted generations produce meaningful partial text worth keeping; a zero-content abort creates no variant.
- The updater state machine already exposes everything the banner needs ("update available" is an existing state of `app/src/lib/updater.ts`).
- v0.1.0 scope stays exactly: variants + banner — nothing else rides along (Q2).

## Validation Strategy (HITL)

1. Regenerate the last answer three times → `<`/`>` cycles "1/3 → 2/3 → 3/3"; each variant shows its model label; the rest of the thread is unchanged.
2. Stop a generation midway → the partial answer survives as a variant marked "aborted".
3. Switch to variant 1, send a follow-up message → the model's next answer reacts to variant 1's content; the variants are gone (only the visible one's text remains, navigation disappeared).
4. Regenerate 11 times → the oldest variant falls off; the readout never exceeds "/10".
5. During a streaming regeneration the `<` `>` buttons are disabled; they come back when the stream ends.
6. Restart the app with variants on the last answer → the variants and the visible one survive the restart.
7. With a `latest.json` publishing a newer version, launch the app → the banner shows without opening Settings; **Install** runs the update; **See what's new** opens GitHub Releases; X hides it until the next launch.
8. **Check for updates** in About still works as before.

## Out of Scope (v0.1.0)

- Variant navigation beyond the last answer; conversation trees (master: rejected).
- Keyboard shortcuts for variant navigation.
- Background/periodic update checks.
- Auto-install without user action.
- Everything in the master's Out of Scope for the beta line.
